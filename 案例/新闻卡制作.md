# 媒体交付复盘案例与方法

一次媒体交付已经获用户验收并完成交付。复盘却发现两个差距：恢复记录还指向较早的草稿；标记为“恢复原始音轨”的新版与前版音轨相同。这个真实案例适合检验人类和 Agent 如何分工。

## 成功结果为什么还需要复盘

用户修正了表达并要求核对早期音轨，最终批准交付。业务结果有效，但不能反过来证明中间每次返修有必要。机器检查显示两个媒体文件容器不同，而音轨数据相同，所以不能声称那次来源修订改变了声音。

原先任务框架也有真实失败：外部技能路径通过符号链接越出项目，被路径边界拒绝；初始合同已经注册，临时改输入又触发不可变保护。后来制作继续，状态却没有跟上。这里首先需要运行侧修复注册前预检和恢复指针，不应让用户每次贴出整段历史。

## 人类可以怎样反馈

如果你记得目标素材，给出已知的唯一标识，说明关注歌曲、片段、音量还是来源。如果只记得“更早那条”，告诉 Agent 查项目记录即可；不要替它翻所有文件，也不要凭感受指定技术原因。

> 当前版本的配乐不符合我的目标。请沿项目里已经留存的素材证据查原文件和片段起点，比较实际变化；保留当前画面。如果听到的声音相同，先报告来源修订的真实影响。

如果你只是要求来源正确，没有要求换声音，就不应顺带扩大到重混音或重做画面。Agent 应先说明预期影响，再报告实际结果。

## 验收边界怎样表达

对成片说“通过”是在确认该版本的创作结果。交付文件是否一致、恢复入口是否正确、框架是否通过、是否可以发布，应各有证据和真实授权。人类不需要替技术系统补写批准；也不能因为框架 blocked，就把已完成的成片重新标为未制作。

后续局部修复记录了依赖预检、按文件身份绑定恢复指针，以及识别“文件不同但音轨相同”的检查。仍有版本治理缺口；这些结果不证明整个流程完整，也不证明营销效果提升。

## 哪些经验可以迁移

适用于媒体、代码部署、文档和数据交付：返修前明确对象，返修后验证实际变化；已交付成果与新增修复分开报告；恢复记录由 Agent 维护。具体音乐、版式、帧数和工具名称留在原项目，不推广成通用要求。

这仍是单个案例。没有发布数据证明传播效果，也没有可比任务证明节省多少时间。可以在下一次同类任务检查素材追溯返工和恢复错误是否复发。
