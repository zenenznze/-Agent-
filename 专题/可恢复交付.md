# 可恢复交付

你已经收到了可用成果，下一次让 Agent 继续，它却说“还没有开始制作”。这往往是恢复记录过期，继续补上下文只能暂时盖住问题。

## 把三件事分开看

业务验收回答“成果符合目标吗”；工具或框架验证回答“声明的流程和证据能否通过检查”；仓库交付回答“预期文件是否进入对应提交和远端”。它们可能在不同时间完成。对于非仓库任务，第三项按实际交付渠道替换，不能凭空要求 Git。

媒体交付案例中，最终成果、批准、交付文件和版本记录都有证据，但任务指针还停在较早草稿，流程入口被外部依赖路径阻塞。因此业务成功与框架缺口同时成立。不能撤销已审成片来“重走流程”，也不能把成片通过写成框架全通过。

## 恢复包应引用什么

跨会话、长任务或多执行者任务，Agent 应维护一个项目内的恢复入口，引用当前目标、当前产物身份、真实批准、交付证据、剩余动作和负责者。技术系统决定具体字段；人类无需指定每一个 JSON 名称。

你可以提出一个可检验条件：

> 在新会话从项目恢复入口继续时，应找到我实际验收的版本和真实剩余项；旧记录不能触发重复制作、重复费用或错误批准。请通过实际回读验证。

文件名和“最新”标签不足以证明版本。媒体、源文案、工具依赖和批准对象都可能不同；Agent 应用对应身份信息核对。更新摘要也不能清掉验收失败、未消费反馈或缺失批准。

## 怎样验收恢复能力

让执行方通过同一入口读取当前任务，核对显示版本和交付证据，然后重复读取，确认没有额外制作或副作用。对于可安全执行的任务再做进程或会话恢复；不要用生产重启来模拟一个低风险测试。

若修复只能恢复业务指针，框架仍 blocked，应接受准确的分层报告，并要求把缺口定位到具体依赖或治理动作。系统故障归运行侧修复；人类只决定真正的业务范围和批准对象。

一次状态检查通过，不能证明断电持久性、跨设备恢复或任意多 Agent 正确。每增加一种保证都应有新的真实场景证据。
